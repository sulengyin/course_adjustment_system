# 13 · 调课对象推荐规则：代课与对调（P7H）

> **术语**（与 `docs/domain-glossary.md` §7 一致）：
> **调课**是总称，包含四种方式——**代课**（一节课单向交给另一位教师上）、**对调**（两人各让出一节课互换）、**调整时间**（改日期或节次，教师不变）、**停课**（取消课次）。
> 本文的"候选名单"指**代课**对象；"对调对象"与"可让出课次"见 §7.7。

## 1. 为什么要有这一节

发起调课时，"调课给谁"原来是把全校教师名单平铺给发起人（144 人量级），由老师自己从名单里挑。
结果是：挑到当时有课的人，方案提交后撞 `TEACHER_SLOT_CONFLICT` 被打回；挑到没教过这门科的人，
对方即使同意也接不下来。推荐要做的事只有一个——**把"更可能接得下"的人排到前面，并说清楚为什么**。

## 2. 规则的定位（边界，先讲清楚）

| 说清楚 | 不说 |
| --- | --- |
| 依据可核验的排课事实排序 | 不评价教师能力、不给"好坏"分 |
| 推荐置顶，其余仍可选 | 不强制发起人只能选推荐名单内的人 |
| 只做只读计算，不写库、不建方案 | 不代替任何人的本人确认 |
| 只有该课次的现任授课教师能拉名单 | 不把全校课表暴露给无关账号 |

推荐不产生任何审计事件、不改变确认集合：确认集合仍由 `projectChange` 按"责任是否改变"计算，
与推荐无关。

## 3. 打分口径

**术语**：全文的"任教"一律指**本学期当前有效的排课**（`teaching_template` 中未撤销的模板），
不是"历史上教过"。撤销过的模板已不代表现在的任教关系，不计入。

事实来源（两类，都取自库内排课数据，不新增维护项）：

- **本学期任教安排**（有效模板）：判断本学期在教哪个班、哪个年级、哪门科目；
- **当天课表**（`occurrence` + `assignment_state`）：判断"该节次是否已有课""当天课程密度"。

档位（同班 > 同年级 > 跨年级）：

| 档位 | 判定 |
| --- | --- |
| `SAME_CLASS` | 本学期任教该班级（任意科目） |
| `SAME_GRADE` | 本学期未任教该班，但任教同年级其他班 |
| `CROSS_GRADE` | 本学期与该班、该年级都没有任教关系 |

## 3.1 档位是主排序键（关键口径）

**同一个班的其他任课教师，即使科目不同，也优先于任何其他班级的同科教师。**
理由是：要接的是这个班的一节课，熟悉这个班（认识学生、知道进度）比科目对口更能决定"能不能立刻接下"；
科目对口与课密度只在档位内部起作用，**不得跨档位翻转顺序**。

| 档位基础分 | 值 |
| --- | --- |
| 任教该班 | 60 |
| 任教同年级其他班 | 30 |
| 跨年级 | 0 |

档位内加分：

| 项 | 分 |
| --- | --- |
| 本学期任教同一科目 | +20 |
| 当天课程密度 | +max(0, 8 − 当天课数)，即当天越空分越高 |

相邻档位相差 30，大于档位内加分上限（20 + 8 = 28），因此档位顺序不会被加分翻掉。
举例：`同班·不同科·当天 8 节` = 60 > `同年级·同科·当天 0 节` = 58 > `跨年级·同科·当天 0 节` = 28。

排序键依次：**档位 → 综合分降序 → 教师 ID 升序**。
前提是"该节次没有课"：那不是筛选口径，是撞课，见 §3.2。
教师 ID 作为最后的稳定键，保证同一份数据两次调用给出同一顺序。

## 3.2 该节次已有课 = 撞课，不是偏好

代课是"把这节课交给另一位教师上"。如果对方在同一时段正在别的班上课，
他没法同时出现在两个教室——这不是"匹配度低"，是接不了。

因此这条不设开关、不随学校口径变化：该节次有课的教师**不进入代课候选**，
只在候选下方按人列出原因（"该节次本人有课（第 N 节），无法同时接手"），
不允许让人悄悄消失。

要让对方把那一节也让出来，走的是**对调**（§7.7），不是代课。
代课流程一次只解决"这一节交给谁"，不承担连锁调课。

## 4. 候选展示

界面只有一组候选：`可代课（该节次本人无课，按匹配度排序）`。

因该节次有课而未列出的教师，在名单下方统一说明人数与原因，例如
`另有 6 位教师未列出：张三（该节次本人有课（第3节），无法同时接手）、…`。
候选不是"全校名单平铺"，后端返回 `excluded` 就是为了让人知道谁被跳过了、为什么。

选中任一教师后，界面显示该候选的全部理由，例如：
`任教该班：本学期任教这个班；本学期任教同一科目；该节次本人无课；当天已排 3 节`。
没有命中任何匹配项时，也如实显示"该节次本人无课 / 当天没有排课"，不编造推荐原因。

候选人本人不在候选里；不在教师名册中的 ID 一律不作为候选。

## 5. 接口

```
GET /api/changes/candidates?termId=...&occurrenceId=...
Authorization: Bearer <token>
```

- 200： `{ ok: true, occurrence: {...}, candidates: [{ teacherId, teacherName, tier, score, teachesSubject, freeAtSlot, dayCount, reasons }] }`
- 400： 缺 `termId` 或 `occurrenceId`
- 403： `NOT_A_TEACHER`（无教师身份）/`NOT_OWNER`（不是该课次的现任授课教师）
- 404： `OCCURRENCE_NOT_FOUND`
- 409： `OCCURRENCE_CANCELLED`（课次已停，不存在"调课给谁"的问题）

路由必须排在 `/api/changes/:id` 之前，否则会被方案详情的正则吃掉（已在代码注释中标注）。

## 6. 验证

- `tests/domain/candidate.spec.ts`：档位顺序、同学科优先、无课优先、密度优先、排除本人与名册外 ID、排序稳定。
- `tests/service/candidate.spec.ts`：`freeAtSlot` 与当天课表逐人一致；他人课次返回 `NOT_OWNER`；课次不存在不猜测。
- `tests/server/http.spec.ts`：接口 200 / 400 / 404 / 403，以及无课候选排在前面。

## 7. 候选筛选偏好（P7I）：系统不替学校把口径写死

调课该优先考虑什么、哪些人不考虑，是学校与教师自己的判断，不是系统能定的。
因此全部做成**可配置**：课务管理人员设全校默认值，教师可在自己的偏好里覆盖。

### 7.1 维度清单

**正面排序（勾选才参与排序）**

| 维度 | 说明 |
| --- | --- |
| 任教该班 | 档位基础分，最高优先级 |
| 任教同年级 | 档位基础分，第二档 |
| 任教同一科目 | 档位内加分 +10（代课不要求同科，跨学科不重罚，统一低固定值） |
| 当天课时少 | 档位内加分 +max(0, 8 − 接手后当天课数) |

**只提示、永不排除**

| 项 | 说明 |
| --- | --- |
| 该班当天同一科目节数 | 达到阈值时只在理由里提示，例如"该班当天该科目共 2 节"。判断权留给人：有的学校体育连排是常态，系统不做对错判定。 |
| 语数教师接手后只剩第4节 | 语数教师当天原本没课、调入的又是上午第4节时提示"可能需专程到校"，见 §7.6。只提示，不排除、不影响排序。 |

**反面排除（勾选才隐藏；被隐藏者连同原因一并返回）**

| 项 | 默认 | 说明 |
| --- | --- | --- |
| 接手后连上 ≥ N 节 | 关，N=3 | 只看**教师本人**连堂，不看班级连堂 |
| 接手后当天超过 N 节 | 关，N=6 | 与"课时少"加分不同，这是硬阈值 |

"该节次本人有课"不在这张表里：它是撞课，不是口径，见 §3.2，任何偏好都不会把它放回候选。

### 7.2 生效顺序与默认

个人偏好 > 全校默认 > **中性默认**。中性默认＝全部维度参与排序、不隐藏任何人，
**唯一例外是撞课**——那是物理冲突，不属于"替教师做减法"。
即：开箱即用只排序；撞课者不列，但连同原因说明。

### 7.3 接口

| 方法 | 路径 | 谁可以 |
| --- | --- | --- |
| GET | `/api/preferences/change` | 已登录；返回生效偏好、来源、全校默认、个人偏好、`canEditSchool` |
| PUT | `/api/preferences/change` | 有教师身份者改自己的（身份即授权） |
| PUT | `/api/preferences/change/school` | 课务管理人员（`CHANGE_L1_CONFIG`）；管理员不代管课务参数 |
| POST | `/api/changes/candidates/preview` | 发起人：把界面临时改过的筛选条件算一遍，不落库 |

偏好不是业务事实，**不写审计链**；偏好只影响"给发起人看的排序与显示"，
**不影响**确认集合计算与冲突判定——这条边界不开放。

### 7.4 界面：口径在设置页，发起调课的屏幕只留必要信息

**偏好只在"设置"页**（顶栏"设置"按钮，全局唯一入口）：列出当前生效口径的来源
（我的偏好 / 全校默认 / 系统默认）、排序考虑项、排除项与提示阈值，并可"保存为我的偏好"；
具备课务管理身份时额外出现"设为全校默认"。

**新建调课方案页不放任何筛选开关**——发起那一刻屏幕上只有"这节课、改成什么、给谁"。
候选按设置页里定好的口径给出，被排除的教师仍如实说明数量与原因。

后端同时支持两种调用：`/api/changes/candidates/preview` 带 `preference` 是界面实时试算（不落库），
不带 `preference` 则按调用者的生效偏好（个人 > 全校 > 中性）计算。

**代课对象不用原生下拉框**，而是页面内的可滚动名单（按钮展开／收起，带姓名过滤）：

- 全校候选上百人，原生下拉在部分浏览器（尤其平板、手机）会把选项渲染成一层浮层，
  点击它的滚动条会把整层关掉，等于选不了人；页面内滚动是真实 DOM 滚动，不受此影响。
- 名单只有"可代课（该节次本人无课）"一组，按匹配度排序，每行带档位与理由；
  该节次有课的教师在下方统一说明人数与原因，不进入名单。
- 没选人就提交时界面直接提示，不把错误留到服务端。

### 7.5 候选算不出来时，绝不退回"全校名单平铺"

候选名单只有三种状态：计算中、已就绪、不可用。

- **计算中**：名单区显示"正在按规则计算候选…"，选择教师的按钮禁用。
- **不可用**：显示具体原因（未改密／没有教师档案／不是自己的课次／课次已停／网络不通等），
  提供"重试"，**不列出任何教师姓名**，提交被拦住。
- 只有**已就绪**才展开名单供选择。

理由：候选不可用时把全校一百多人平铺出来，等于让老师盲选，
把本可以在发起前发现的冲突推到提交之后——这正是系统要避免的。
"不强制选推荐名单"指的是推荐之外的人仍可选，不是"没有推荐时也照给一份全量名单"。

### 7.6 语数教师接手后只剩上午第4节：只提示，不排除

**触发条件**（三条同时成立）：

1. 候选教师 B **本学期任教语文或数学**（按科目名判定，不按科目 ID 写死）；
2. B 在调入日**当天原本没有其他课**（`dayCount = 0`）；
3. 调入的节次是**上午第 4 节**（`targetPeriod = 4`）。

此时在候选理由后面追加提示：`接手后当天只有上午第4节这一节，可能需专程到校`。

**为什么等价于"只剩这一节"**：代课只会让接手方的课变多，不会变少。
所以"接手后当天只剩一节"必然等于"原本 0 节 + 调入的这一节"，
条件 2 与条件 3 同时成立即可判定，不需要额外算"调后课表"。

**为什么只提示**：这是对"对方会不会答应"的**推测**，不是排课事实。
被提示的教师仍然完整参与排序、仍然可选；发起人看到提示后自行决定要不要换人。
若做成排除，等于系统替教师拒绝，与 §2 "推荐不强制"的定位冲突。

**与"当天课时少加分"的关系**：维度 `lightLoad` 会给当天课少的候选加分（`+max(0, 8−调后课数)`），
这里提示的恰恰是"课少到只剩一节"的极端情形。两者不矛盾——加分是"更可能接得下"，
提示是"他可能要专程跑一趟"。一个调排序，一个给事实，互不覆盖。

**不覆盖的情形**（明确不做，避免以后被误加）：

- 孤节在第 1–3 节：人上午本来就要到校，不构成额外负担；
- B 当天还有别的课：多一节不改变"人已在校"的事实；
- 非语数教师：同样的空课日不算同一类风险（语数课时密集，空课日更可能是原本不需到校）；
- 只对代课（`REASSIGN`）生效；调整时间（`MOVE`）没有接手方，不产生此提示；
  跨天对调是另一种场景，见 §7.7。

### 7.7 跨天对调：先选人，再选课

**为什么单列**：§7.6 只看"接手日"。代课时对方的课只会变多，永远算不出"少一节"。
真正会让对方**少一节课**的，是跨天对调：A 的周二课交给 B，B 的周五课交给 A，
两条 `REASSIGN` 放进同一笔方案，双方各自确认。

**流程**：

1. 发起人选中自己的一节课；
2. 从候选名单里选对调对象 B（沿用 §3 的排序，只列该节次无课的教师）；
3. 系统列出 B 本学期**可让出的课次**：日期、节次、班级、科目，以及"让出后 B 当天还剩几节"、
   "你接手后当天几节、最长连着上几节"；
4. 选中一节后提交，生成两条 `REASSIGN`，必要确认人为 A 与 B。

**发起人自己的连堂**（两侧都要算）：

对调不是单向的：B 接手我这一节，我也接手 B 那一节。所以除了 B 在我这一天的课表，
还必须算**我在 B 那一天的课表**：

```
我在 B 那天的课 = 原有节次
               −（同一天时）我让出的那一节
               + 我接手的那一节
```

再用同一套 `longestRun` 判连堂。结果放在 `myDayCountAfter` / `myLongestRunAfter`，
理由写成 `对调后你当天 5 节`、`对调后你连续上 3 节`。

达到 `consecutiveLimit`（默认 3）时：

- 默认 → 进 `warnings`：`对调后你会连续上 3 节（原本 2 节），达到 3 节上限`。
  该课次**仍可选**，但排在没有任何警告的课次之后，界面上单独标黄；
- 学校或教师勾了"接手后连上 ≥ N 节" → 升级进 `blockedReasons`，该课次不可选。

判定看的是**换完之后实际连着上几节**，不是"比原来多了几节"：原本已经 4 连、
换完还是 4 连，对当事人仍然是连上 4 节的事实，不该因为"没变长"就不提。
括号里的"原本 N 节"是给他判断用的参照。

若可选的课次全部带警告，界面在列表上方说明一句
`这 N 节课换完之后你都会连堂`，避免满屏标黄让人以为系统坏了。

为什么默认只警告：连着上完早点走是常见的自愿选择，值不值得由当事人判断；
系统只负责把"换完之后你会连着上几节"算准并摆在面前，不替他做决定。

**提示规则**（只提示、不排除）：B 本学期任教语文或数学，且让出该节后当天

- 一节不剩 → `对调后该教师当天没有课`
- 或只剩上午第 4 节 → `对调后该教师当天只有上午第4节这一节，可能需专程到校`

**不可选的组合**（`blockedReasons`，原因照实返回，不静默丢弃）：

- 发起人在对方那一节的时间另有课（除本次要换出的这一节外）；
- 对方在发起人这一节的时间另有别的课（否则换过来会撞课）；
- 偏好开启连堂上限时，对方或发起人任一侧接手后达到上限。

**接口**：

```
GET /api/changes/swap-options?termId=...&occurrenceId=...&teacherId=...
```

返回 `{ ok, occurrence, counterpart, options: [{ occurrenceId, date, period, className, subjectName, remainingCount, hints, warnings, blockedReasons, myDayCountAfter, myLongestRunAfter }] }`，
按"可选优先 → 无连堂警告优先 → 无提示优先 → 日期节次"排序。仅该课次现任授课教师可调用。

### 7.8 对调对象推荐：只推同班教师，落点必须具体到"日期 + 第几节"

§7.7 只解决了"选了人之后看哪些课次"。真正要回答的第一个问题是**该推谁**，
这里的口径是收窄的：

| 组 | 谁在里面 | 依据 |
| --- | --- | --- |
| **推荐** | 本学期任教**该课次所在班**，且至少有一节可换的课 | 同班教师熟悉学生与进度，换过去对班级扰动最小 |
| **不推荐** | 其他全部教师，逐人给理由 | 不隐藏任何人，理由必须写出来 |

**为什么必须落到课次**：只给一个名字等于把判断丢回给老师——同一位教师可能这周有三节可换、
也可能一节都换不了。推荐项必须带 `日期 + 节次 + 班级 + 科目`，否则"和谁换"仍然是一句空话。

**不推荐的四种理由**（都写进 `reasons`，界面上直接可见）：

1. `本学期不任教该班（同年级）` / `（跨年级）`——班级不符合；
2. `本学期没有可让出的课次`——同班但没有课；
3. `该教师剩余的课次都已过去，无法对调`——有课，但全在 §7.9.1 的"今天之前"；
4. `可让出的课次都不可行` + 具体冲突（你在该时段已有课 / 对方在你这一节还有别的课 /
   超过连堂或当天总量上限 / 与你这节课时长不等，见 §7.9.2）。

**同班之外仍可选**：推荐只是排序建议，不是权限。界面把两组都列出来，不推荐者也可点开选课；
这与 §2 "推荐置顶，其余仍可选"一致。

**偏好的作用方式**（与代课共用一套维度，但有两处必须区别）：

- 撞课不按维度判：对调本来就是一节换一节，对方在发起人这一节有课可能正是要换的那一节。
  所以只在逐节课次上算"换完之后会不会同时在两处"，不在选人阶段统一排除；
- 当天课数与连堂按"换完之后"实算，两侧都算：对方让出一节、接手一节；发起人同样。
  按 `+1` 近似会把同一天换课误判成超量。

**接口**：

```
GET /api/changes/swap-candidates?termId=...&occurrenceId=...
```

返回 `{ ok, occurrence, recommended: [...], notRecommended: [...], preferenceSource }`。
每位教师带 `tier`、`viableCount`、`sampleOptions`（最多 3 节，含日期与节次）、`reasons`、`hints`；
完整课次列表仍由 §7.7 的 `swap-options` 按需拉取，避免一次返回整学期几千条。

**界面默认**：新建调课方案的「变更方式」默认选中**对调**，进页面即按对调计算对象；
要改成代课、调整时间或停课，由用户自己切换。理由：教师之间最常见的是互换，
默认落在代课等于每次都要多点一次。四种方式的选项顺序也按此排列，
避免"下拉第一项"与"默认值"不是同一个，让人以为没切成功。

### 7.9 对调的两条硬性前提：课还没发生、两边单节时长相等

这两条不是"偏好"，是"做不到"，所以它们进 `blockedReasons`（界面不可选 + 写明原因），
不进 `reasons`（推荐理由），也不受任何人关闭偏好的影响。

#### 7.9.1 已经过去的课不能再调

- 对方**早于今天**的课次**直接不出现在列表里**——那是既成事实，列出来只会让人白点一次；
- 发起人**自己那节课已经过去**时，列出的每个课次都不可选，理由写明「你要调出的这节课已经过去（日期），不能再调」。

"今天"取**服务器本地日期**，不是 `toISOString().slice(0,10)`：后者是 UTC 日期，
东八区每天 00:00–08:00 会算成前一天，过去/未来的判定会整体错一天。
界面上的"今日列"同样按服务端时间算，两边口径一致。

#### 7.9.2 单节时长不等，不能对调

对调是两节课"整段互换"：我让出一节、接手一节，对方反过来。
时长不等就意味着有一方的课时被凭空增减——这不是换课，是减课。

真实作息的实测值（`TERM-2026-08-31`）：

| 节次 | 起止 | 时长 |
| --- | --- | --- |
| 第 1–3 节 | 08:20–11:05 | 40 分钟 |
| **第 4 节** | **11:20–11:40** | **20 分钟** |
| 第 5–6 节 | 13:00–14:35 | 40 分钟 |
| 第 7 节 | 15:05–15:40 | 35 分钟 |

所以：**第 4 节只能和第 4 节对调（可跨天）**，任何 40 分钟的课都不能和第 4 节互换。
第 7 节（35 分钟）同样不能和第 1–3、5、6 节（40 分钟）互换——这是同一条规则的自然结果，
不是又加了一条特例。

**判定方式**：比较两节课的实际起止时间（`lessonMinutes`），不写死节次号。
换一套作息表（比如第 4 节改成 40 分钟）不需要改代码。

**缺时间怎么办**：课次没有结束时间（`certainty=UNKNOWN`）时算不出时长，一律不可对调，
理由写「该课次缺少起止时间，无法确认时长是否相等」。宁可少推荐，不留一个"可能换了不等长课"的口子。

**为什么不只提示**：§7.6 / §7.7 的"只剩第 4 节""当天没课"是对**对方会不会答应**的推测，
所以只提示；而时长不等是**换完之后课时总量对不上**，是事实层面的错误，必须挡住。

**连带影响**：`swapCandidates` 的 `viableCount` 只统计同时满足"未过去 + 同时长 + 不撞课"的课次，
所以推荐组会明显变少。这是规则的必然结果，不是数据少了。

### 7.10 代他人发起：能力单点授予，归属仍是被代教师

**谁能做**：只有持有账号级能力 `CREATE_CHANGE_ON_BEHALF` 的账号。
角色表里所有角色都是 `DENY`——管理员也不例外，且不能授给自己。
授予必须登记依据，见 `docs/permission-matrix.md` 文末。

**这笔方案算谁的**：

| 字段 | 记谁 | 为什么 |
|---|---|---|
| `submitted_by` | 被代教师 | 业务上这是他的调课，他的课表、他的责任 |
| `created_by` | 代办人 | 出事要能追到"实际是谁点的提交" |
| 必要确认者 | 按课次计算，仍含被代教师 | 代发起不等于代同意 |

**不变的那条线**：被代教师本人不确认，方案不会生效。系统不会因为"有人代他发起了"
就视为他同意；`docs/03` 的"不得以一方填写推定他人确认"在这里同样成立。

**对调时最容易错的一处**：对调是两条 `REASSIGN`。
- 第一条：被代教师的课 → 换给对调对象；
- 第二条：对调对象的课 → 换给**被代教师**，不是换给代办人。

写成代办人会把课直接挪到代办人名下，属于事实错误。服务端 `resolveInitiator` 只定"方案算谁的"，
两条 `REASSIGN` 的 `toTeacherId` 由调用方给，界面必须按被代教师填。

**课次归属校验**：服务端要求 items 中至少有一条当前属于被代教师（与本人发起的
"至少一条属于我"同一条规则），否则拒绝。这样既挡住"拿别人的课代发起"，
又不妨碍对调（第二条本来就不属于他）。

**界面**：两个入口，都要先搜索选人（输入才出名单，不铺全校教师）：

1. **课表页 → 查看其他老师课表 → 点一节课**。选中教师后，本人的课表整体收起，
   页面换成对方那张表（`#timetable-other`，`#timetable-mine` 置 `hidden`），
   避免两张同形表格上下叠着、点错一格就以别人的名义建单。点任意一节直接跳到
   "新建方案"，并自动进入代发起、选中该课次；对方已停课的课次不可点。
   没有 `CREATE_CHANGE_ON_BEHALF` 的人看到的仍是纯只读视图——格子是 `div` 而非 `button`。
2. **调课页 → 新建方案 → 代其他老师发起**。先切换模式再选人；选中后课次下拉整体换成
   该教师本周的课次。提交时带 `onBehalfOfTeacherId`。
