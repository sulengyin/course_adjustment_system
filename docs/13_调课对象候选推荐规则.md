# 13 · 调课对象候选推荐规则（P7H）

## 1. 为什么要有这一节

发起调课时，"改派给谁"原来是把全校教师名单平铺给发起人（144 人量级），由老师自己从名单里挑。
结果是：挑到当时有课的人，方案提交后撞 `TEACHER_SLOT_CONFLICT` 被打回；挑到没教过这门科的人，
对方即使同意也接不下来。推荐要做的事只有一个——**把"更可能接得下"的人排到前面，并说清楚为什么**。

## 2. 规则的定位（边界，先讲清楚）

| 说清楚 | 不说 |
| --- | --- |
| 依据可核验的排课事实排序 | 不评价教师能力、不给"好坏"分 |
| 推荐置顶，其余仍可选 | 不强制发起人只能选推荐名单内的人 |
| 只做只读计算，不写库、不建方案 | 不代替任何人的本人确认 |
| 只有该课次的现任授课教师能拉名单 | 不把全校课表暴露给无关账号 |

推荐不产生任何审计事件、不改变确认集合：确认集合仍由 `projectChange` 按"责任是否改变"计算，
与推荐无关。

## 3. 打分口径

**术语**：全文的"任教"一律指**本学期当前有效的排课**（`teaching_template` 中未撤销的模板），
不是"历史上教过"。撤销过的模板已不代表现在的任教关系，不计入。

事实来源（两类，都取自库内排课数据，不新增维护项）：

- **本学期任教安排**（有效模板）：判断本学期在教哪个班、哪个年级、哪门科目；
- **当天课表**（`occurrence` + `assignment_state`）：判断"该节次是否已有课""当天课程密度"。

档位（同班 > 同年级 > 跨年级）：

| 档位 | 判定 |
| --- | --- |
| `SAME_CLASS` | 本学期任教该班级（任意科目） |
| `SAME_GRADE` | 本学期未任教该班，但任教同年级其他班 |
| `CROSS_GRADE` | 本学期与该班、该年级都没有任教关系 |

## 3.1 档位是主排序键（关键口径）

**同一个班的其他任课教师，即使科目不同，也优先于任何其他班级的同科教师。**
理由是：要接的是这个班的一节课，熟悉这个班（认识学生、知道进度）比科目对口更能决定"能不能立刻接下"；
科目对口与课密度只在档位内部起作用，**不得跨档位翻转顺序**。

| 档位基础分 | 值 |
| --- | --- |
| 任教该班 | 60 |
| 任教同年级其他班 | 30 |
| 跨年级 | 0 |

档位内加分：

| 项 | 分 |
| --- | --- |
| 本学期任教同一科目 | +20 |
| 当天课程密度 | +max(0, 8 − 当天课数)，即当天越空分越高 |

相邻档位相差 30，大于档位内加分上限（20 + 8 = 28），因此档位顺序不会被加分翻掉。
举例：`同班·不同科·当天 8 节` = 60 > `同年级·同科·当天 0 节` = 58 > `跨年级·同科·当天 0 节` = 28。

排序键依次：**该节次无课 → 档位 → 综合分降序 → 教师 ID 升序**。
可行性优先于匹配度：能直接接下的，一律排在"需要先对调"的前面。
教师 ID 作为最后的稳定键，保证同一份数据两次调用给出同一顺序。

## 4. 候选展示

界面分成三组（`optgroup`），推荐组置顶：

1. `推荐（该节次本人无课，按匹配度排序）`
2. `该节次有课 · 需先与对方对调`
3. `其他教师`

选中任一教师后，界面显示该候选的全部理由，例如：
`任教该班：本学期任教这个班；本学期任教同一科目；该节次本人无课；当天已排 3 节`。
没有命中任何匹配项时，也如实显示"该节次本人无课 / 当天没有排课"，不编造推荐原因。

候选人本人不在候选里；不在教师名册中的 ID 一律不作为候选。

## 5. 接口

```
GET /api/changes/candidates?termId=...&occurrenceId=...
Authorization: Bearer <token>
```

- 200： `{ ok: true, occurrence: {...}, candidates: [{ teacherId, teacherName, tier, score, teachesSubject, freeAtSlot, dayCount, reasons }] }`
- 400： 缺 `termId` 或 `occurrenceId`
- 403： `NOT_A_TEACHER`（无教师身份）/`NOT_OWNER`（不是该课次的现任授课教师）
- 404： `OCCURRENCE_NOT_FOUND`
- 409： `OCCURRENCE_CANCELLED`（课次已停，不存在"改派给谁"的问题）

路由必须排在 `/api/changes/:id` 之前，否则会被方案详情的正则吃掉（已在代码注释中标注）。

## 6. 验证

- `tests/domain/candidate.spec.ts`：档位顺序、同学科优先、无课优先、密度优先、排除本人与名册外 ID、排序稳定。
- `tests/service/candidate.spec.ts`：`freeAtSlot` 与当天课表逐人一致；他人课次返回 `NOT_OWNER`；课次不存在不猜测。
- `tests/server/http.spec.ts`：接口 200 / 400 / 404 / 403，以及无课候选排在前面。

## 7. 候选筛选偏好（P7I）：系统不替学校把口径写死

调课该优先考虑什么、哪些人不考虑，是学校与教师自己的判断，不是系统能定的。
因此全部做成**可配置**：课务管理人员设全校默认值，教师可在自己的偏好里覆盖。

### 7.1 维度清单

**正面排序（勾选才参与排序）**

| 维度 | 说明 |
| --- | --- |
| 任教该班 | 档位基础分，最高优先级 |
| 任教同年级 | 档位基础分，第二档 |
| 任教同一科目 | 档位内加分 +10（调课不是代课，跨学科不重罚，统一低固定值） |
| 当天课时少 | 档位内加分 +max(0, 8 − 接手后当天课数) |

**只提示、永不排除**

| 项 | 说明 |
| --- | --- |
| 该班当天同一科目节数 | 达到阈值时只在理由里提示，例如"该班当天该科目共 2 节"。判断权留给人：有的学校体育连排是常态，系统不做对错判定。 |

**反面排除（勾选才隐藏；被隐藏者连同原因一并返回）**

| 项 | 默认 | 说明 |
| --- | --- | --- |
| 该节次本人有课 | 关 | 有课不等于不能调，往往正是要找有课的人对调 |
| 接手后连上 ≥ N 节 | 关，N=3 | 只看**教师本人**连堂，不看班级连堂 |
| 接手后当天超过 N 节 | 关，N=6 | 与"课时少"加分不同，这是硬阈值 |

### 7.2 生效顺序与默认

个人偏好 > 全校默认 > **中性默认**。中性默认＝全部维度参与排序、不隐藏任何人。
即：开箱即用只排序、不替教师做减法。

### 7.3 接口

| 方法 | 路径 | 谁可以 |
| --- | --- | --- |
| GET | `/api/preferences/change` | 已登录；返回生效偏好、来源、全校默认、个人偏好、`canEditSchool` |
| PUT | `/api/preferences/change` | 有教师身份者改自己的（身份即授权） |
| PUT | `/api/preferences/change/school` | 课务管理人员（`CHANGE_L1_CONFIG`）；管理员不代管课务参数 |
| POST | `/api/changes/candidates/preview` | 发起人：把界面临时改过的筛选条件算一遍，不落库 |

偏好不是业务事实，**不写审计链**；偏好只影响"给发起人看的排序与显示"，
**不影响**确认集合计算与冲突判定——这条边界不开放。

### 7.4 界面

新建调课方案页有"候选筛选（可选）"折叠区：勾选即时重算候选，
被当前条件排除的教师会在下方列出姓名与原因（"另有 N 位教师未列出：…"），
并提供"保存为我的偏好"；具备课务管理身份时额外出现"设为全校默认"。
