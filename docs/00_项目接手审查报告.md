## 3. V2.3 与 R05 一致性审查（差异清单）

分级：**S1 = 影响首版范围或技术路线，须先裁定；S2 = 表述/覆盖差异，需补录；S3 = 澄清性说明，不阻断。**

### 3.1 S1 级（阻断首版范围，需项目负责人裁定）

**DIF-01 客户端形态：统一 Web vs "三路线不预先定案"**

- V2.3（已确认，硬性）："统一响应式 Web 应用"，鸿蒙 PC/Windows/macOS/手机用受支持浏览器打开**同一服务**。
- R05 §0.6："钉钉小程序、H5 微应用、独立 Web 均不预先定案"；§4 T01 将"钉钉接入方式选型"列为 OPEN。
- 辨析：两者在**架构层**不冲突（单一后端、单一权威数据、同一 API 契约、同一套业务代码），冲突在**前端载体与登录方式**。若走钉钉内嵌，会引入 JSAPI 免登/组织架构依赖，属于 R05 明令不得擅自决定的事项。
- 处理建议（不代替你决定）：Phase 1–2 采用**载体无关**实现——纯 HTTP/JSON API + 可在标准浏览器运行的前端，不引入任何钉钉专有 SDK、不假设免登、不创建组织应用。待 T01 有结论后再评估是否增加钉钉容器适配层。若你要求现在就锁定浏览器 Web，则 DIF-01 关闭，但仍需保留"未来可嵌入"的接口边界。
- **需要你确认**：第一阶段是否按"载体无关、浏览器可运行"推进？

**DIF-02 导入格式范围：CSV/XLSX vs 出现 "Word 课表"**

- V2.3 FR-04（P0）：支持 CSV/XLSX，含模板映射、预览、校验、差异。
- R05 §4 S01 与 §5 Phase 3：出现"真实 **Word** 格式及导入容差""核验 Word 课表导入"。
- 影响：若学校实际课表是 .doc/.docx（含合并单元格、图片表格），则 P0 导入工作量与验收标准需变更；V2.3 从未把 Word 列入范围。
- 处理建议：导入层做**格式适配器**抽象（解析器可插拔），首版实现 CSV/XLSX；Word 能力在拿到脱敏样本前**不得承诺**，也不得写进验收。另需注意：图片型课表（扫描/截图）属于 OCR 范畴，风险更高，必须单独决策。
- **需要你确认**：S01 能否提供 3–5 份脱敏真实课表（Word/Excel/图片各若干）？

**DIF-03 轮换课计算口径缺失**

- V2.3 仅建模"单双周"（§10 必测场景 3）。
- R05 AC09："轮换课遇假期、缺课、代上 → 不无依据选择'日历奇偶'或'实际授课次数'计算规则"。
- 影响：这是**具体课次生成**（P0 核心能力）的输入条件。若真实课表含轮换课程而口径未定，系统无法确定某天该上哪一轮。
- 处理建议：领域模型预留 `rotation_rule` 概念位，但首版对其只支持"显式指定 + 待核验"表达，**不实现任何自动推算**；遇到轮换课次显示 `UNKNOWN_ROTATION`，不得回退到"按周次奇偶"猜测。
- **需要你确认**：学校是否存在轮换课程？若有，其排定依据由谁提供？

### 3.2 S2 级（覆盖差异，须补录进基线）

**DIF-04 课后服务"备案 ≠ 当天实际占用"（R05 AC13 新增）**

V2.3 将课后服务作为 P0 导入的 `work_obligation`，并允许其参与硬冲突校验（FR-07"已确认的课后服务/值班冲突"）。R05 观察到"初始安排协商后备案，临时互换可不重新备案"，因此备案表不等于当天真实占用。

处理：`work_obligation` 保留 V2.3 的 `certainty` 与 `source_id`，并新增语义——**备案安排是"已知的正式安排"，可作为冲突校验依据，但界面与导出不得表述为"该教师当天实际在校"**。是否需要把"已备案课后服务"降级为软提醒而非硬阻断，属待确认（列入 §5 未决）。

**DIF-05 校外求助的人工代录路径（R05 新增 CONFIRMED，V2.3 完全缺失）**

R05 §0.5 / AC11：校外教师求助 → 人工沟通 → 校内授权人员**代为记录**；代录**不等于**替接课教师确认。

V2.3 只规定"第一版仅校内网络"，未规定外出教师如何求助。此条为**新增已确认约束**，应补入基线。可实现部分：代录记录必须与"本人确认""实际执行"三个独立实体分离，且代录人身份可审计。不可实现部分："谁有权代录"（岗位未定）。

**DIF-06 R05 决策台账不完整（重要）**

R05 §4 只列 D01–D08、T01、S01。V2.3 §A 中明确标注"**未决，用户暂停**"的两项，R05 只覆盖了一项：

| O4-1 通知未送达/电话无人接/已读未接单/明确拒绝/排班无代理如何分类                | 仅被 D07"何时算未解决"概括，丢失"联系失败分类"子问题 | **部分遗漏**，仍 OPEN |

**DIF-07 "年级组长"角色（R05 观察项，V2.3 无）**

R05 §2：普通调课不在年级组长处登记；**代课**通常由年级组长协调、登记。

V2.3 只有抽象的"学校授权人员""课务管理人员"。处理：**不得**把"年级组长"自动映射为系统内的授权登记人/协调人。这是一个 OBSERVED 事实，不是权限授予。权限矩阵中相关行必须保持 `TBD_BLOCKED`，等待 D06/D07 关闭。

**DIF-08 新版课表切换（D03）与 V2.3 "不静默覆盖"的关系**

V2.3 是 DECISION 级约束（"不静默覆盖"），R05 把"新版适用日期 + 与既有有效临时变更重叠如何处理"整条标 OPEN。二者不冲突，但**范围被放大**：不只是"导入不覆盖"，而是"新版课表如何与已生效调课共存"整体未定。

处理：Phase 2 只能实现"冲突队列 + 人工待处理"，**不得**实现任何自动择一、自动失效、自动顺延逻辑。V2.3 §5.1.9.3 "恢复方案等待确认期间原安排仍有效"是 **PROPOSED**，同样不得作为默认实现。

**DIF-09 部署硬件表述漂移**

V2.3："学校可提供**一台持续运行的电脑**"，OS/拓扑/责任待核查。  
R05："**校内服务器**与教师 Wi-Fi 均可访问互联网"，但"教师 Wi-Fi → 校内服务器可达性未证实"。

处理：视为同一件事的两种表述，但需实测确认硬件形态。若实际是办公 PC（可能 Windows、可能休眠/关机），则部署包必须支持"非 Linux、无容器、无管理员权限"的降级路径——这会影响技术选型，属 TECH-TEST 阻塞项。

**DIF-10 AC05 与 R02-B3 的边界重叠**

R05 AC05："教师 A 表示 B 同意但无可核验本人依据 → 不替 B 生成确认"。  
V2.3 R02-B3：**授权人员**可登记"B 电话/当面口头接受"，状态为"待本人补确认"。

两者并非矛盾，但必须精确区分，否则实现会走偏：

| 场景               | 允许产生                           | 不得产生             |
| ---------------- | ------------------------------ | ---------------- |
| 普通教师 A 转述"B 同意了" | 无（可作备注/附件，不进入确认链）              | 任何"待补确认/口头接受"记录  |
| 学校授权人员登记"B 电话接受" | 口头接受记录（含渠道、发生时间、登记时间、登记人、方案版本） | "B 已确认"、正式生效、已执行 |
| B 本人登录补确认        | 本人确认（真实提交时间，不倒填）               | 把补确认回写为电话时刻      |

**DIF-11 校外访问：从"不做"升级为"必须拒绝"**

V2.3："本版不实现校外访问"（能力缺失）。  
R05 §0.5："校外**不能直接**访问业务系统"（安全属性）。

处理：这是可验收的增强要求，需在部署阶段实测"校外手机移动数据访问被拒绝"，并检查是否存在公网暴露（端口映射、UPnP、云隧道）。架构上要求：服务只绑定内网地址、默认无公网入站、无第三方隧道依赖。

**DIF-12 结算语义（R05 D08 新增）**

V2.3 无薪酬/结算章节。R05：代课记录存在下游工资/补贴用途，但"一节 10 元"只是观察举例，**不是规则**；首版不自动算钱。

处理：数据模型可保留"代课已安排/已实际完成/已提交/可结算/已发放"的**状态区分位**，但**不得**设计金额字段、补贴标准表或自动结算逻辑，否则等于替学校立法。

**DIF-13 P1 通知渠道未定**

V2.3 P1 有"系统内通知和调课单"；R05 明确"钉钉通知及待办"不做，且不得创建正式组织应用。处理：P1 通知仅做**系统内待办 + 站内消息**，渠道适配层留空；不得默认短信/钉钉/微信公众号。

### 3.3 S3 级（澄清，不阻断）

- **DIF-14** R05 §3 的 CONFIRMED 十条已逐条比对 V2.3，**未发现实质冲突**（详见附录 A）。R05 的表述更严格（如"不能从有空推断愿意"），V2.3 同样有此约束，属强化而非改变。
