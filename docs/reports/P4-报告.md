## 1. 本阶段确定的边界

P4 只做"线上本人确认"这一条链：

```
草案 → 提交（计算并固化必要确认者）→ 逐人本人确认/拒绝 → 改案（版本+1）
     → 冲突复核 → 单事务生效 → 审计 → 撤回（未生效）/ 恢复方案（已生效）
```

明确不做：

- 线下调课单、口头代录、电话记录作为确认输入（D01/D02 未关闭）
- 争议裁决、卡单处置（D04）
- 通知送达判定（BIZ-13，当前一律 `UNDETERMINED`）
- 管理员代确认、代拒绝（L0 硬不变量）
- 删除已生效变更（只提供恢复方案）

## 2. 流程与状态

状态机与 `docs/state-machines.md` 一致，代码中由 `canTransition` 强制：

| 从 | 允许到 |
|---|---|
| `DRAFT` | `PENDING_CONFIRMATION`、`WITHDRAWN` |
| `PENDING_CONFIRMATION` | `BLOCKED_CONFLICT`、`APPLYING`、`REJECTED`、`WITHDRAWN`、自身（改案） |
| `BLOCKED_CONFLICT` | `PENDING_CONFIRMATION`、`REJECTED`、`WITHDRAWN` |
| `APPLYING` | `EFFECTIVE`、`PENDING_CONFIRMATION` |
| `EFFECTIVE` / `REJECTED` / `WITHDRAWN` | 无 |

禁止 `PENDING_CONFIRMATION → EFFECTIVE`（跳冲突复核）与 `EFFECTIVE → DRAFT`，均有测试。

## 3. 关键设计取舍

### 3.1 目标时段已有课：不是拒绝理由（纠正 P3 末的错误提问）

变更方案描述的是**变更后的完整结果**，不是"往空格子里塞一节课"。

| 场景 | 系统行为 |
|---|---|
| 调到该班已有课的时段，且方案未安排原课去向 | 报 `CLASS_SLOT_CONFLICT`，状态 `BLOCKED_CONFLICT`，提示补全方案 |
| 调到同一时段，同时把原课取消/移走/改派 | 冲突消失，原课教师自动进入确认集合 |
| 两人互换时段（两条 `MOVE`） | 无冲突，双方各自确认 |

对应测试：`tests/service/change.spec.ts`「只调进已占用时段而不安排原课去向 → 提交即被冲突挡住」，以及 `tests/domain/change.spec.ts` 的互换与顶替两组。

### 3.2 必要确认者在提交时固化

初版实现每次判定都重新计算确认者。测试暴露了一个严重问题：**若课表在确认期间被其他方案改动，确认集合会悄悄换人**——原本该确认的教师被移出，新的教师被加入，而旧确认仍挂在方案上。

修正为：提交/改案时把确认集合写入 `change_required`（按 `revision` 固化）。此后：

- 确认只认固化集合，不在集合内返回 `NOT_A_CONFIRMER`
- 课表版本变化时整单返回 `STALE_VERSION`，不换人、不继续

### 3.3 版本互斥优先于确认检查

两个互斥方案同时推进时，先校验每个课次的 `expected_version`。版本不一致直接返回 `STALE_VERSION`，而不是先报告"确认不足"——后者会掩盖真正的冲突原因。

事务内再次复核版本，避免预检查与写入之间的窗口。

### 3.4 恢复方案只作用于未执行课次

`execution_fact` 只有显式登记才有记录，系统不按时间推断。

| 方案类型 | 遇到已执行课次 |
|---|---|
| 普通变更 `CHANGE` | 整单拒绝 `EXECUTED_NOT_CHANGEABLE`，课表不变 |
| 恢复 `RECOVERY` | 跳过该课次，其余生效，返回 `skippedExecuted` |

恢复条目由调用方给出，系统**不自动生成反向操作**——自动反向等于替学校决定"恢复成什么样"。

### 3.5 纠错只做确定的一半

`classifyCorrection` 只实现"改变授课责任 → `REQUIRES_NEW_PROPOSAL`"。

未改变责任时不放行，返回 `TBD_CORRECTION_SCOPE`（BIZ-01 白名单未定）。没有"默认为资料性纠错"的分支。

## 5. 验收对照（计划 §P4 验收 1–7）

| # | 验收项 | 结果 | 对应测试 |
|---|---|---|---|
| 1 | 必要确认者由受影响集合计算；班主任不进集合但收到通知 | 通过 | 「改派：新旧教师都进入确认集合，班主任只收通知」；「班主任本人责任被改变时因教师身份进入 required」；「班主任未配置时显式暴露」 |
| 2 | 拒绝 / 沉默 / 改案后版本变更 → 不生效 | 通过 | 「无人确认时不能生效」「一人接受、一人沉默仍不生效」「任何人明确拒绝即终止」「改案后旧确认失效」 |
| 3 | 并发两个互斥方案仅一个生效，另一个 409；审计与课表同事务 | 通过 | 「两个互斥方案只有一个生效，另一个因版本过期被拒」 |
| 4 | 同一幂等键重复提交只产生一次变更 | 通过 | 「同一幂等键重复提交只产生一个方案」 |
| 5 | 生效后删除被拒；取消须走恢复方案并重新确认 | 通过 | 「已生效变更不可删除」「已生效方案不能撤回」 |
| 6 | 含已执行课次的方案，恢复只作用于未执行部分 | 通过 | 「恢复方案只作用于未执行课次」 |
| 7 | 改变责任的纠错被拒；纯资料纠错不自动放行 | 通过（识别方向） | 「改变授课责任的纠错一律要求新方案」「未改变责任时不放行」 |

验收 3 的"409"在服务层表现为 `STALE_VERSION`；接入 HTTP 时映射为 409。

## 6. 假设与风险

| 编号 | 假设/风险 | 影响 | 处理 |
|---|---|---|---|
| R-20 | 确认者固化后，确认期间课表变化会导致整单失效 | 教师可能"刚确认完又要点一次" | 这是安全侧取舍：宁可重来，不可换人 |
| R-21 | 版本预检查与事务写入之间仍有极小窗口 | 单进程 SQLite 下无实际并发；多实例部署会暴露 | 多实例前必须改用数据库行锁或串行化事务 |
| R-22 | 通知只产生事件，`delivery` 恒为 `UNDETERMINED` | 不能据此判断"已通知到人" | 符合 BIZ-13 未定；界面不得显示"已送达" |
| R-23 | 恢复条目由调用方提供，系统不生成反向操作 | 调用方可能给错方向 | 生效前仍需全部本人确认，错误不会被静默吞掉 |
| R-24 | `execution_fact` 是 P4 为验收 6 建的最小表 | 争议、核验状态缺失 | P6 扩展；当前只支持"已登记/未登记" |
| R-25 | **服务层不校验调用者身份**：`decide()` 接受传入的 `teacherId` | 若直接暴露为接口，可冒充他人确认 | P5 接入登录后，由路由层用已认证身份调用，禁止从请求体取 `teacherId`；在此之前不得对外暴露 |

R-25 是本阶段唯一的安全缺口。它不违反 L0（代码没有"管理员代确认"的分支），但缺少"确认者就是当前登录人"这一层校验，必须在 P5 补上。

## 7. 进入 P5 的条件

- 无技术阻断。
- D01/D02 仍为 OPEN：系统没有接受线下材料作为确认输入的入口，当前实现不构成违规。
- P5 范围：部署形态、网络边界（仅内网）、登录与身份校验（补 R-25）、备份恢复。
- T-02（服务器 OS/Node 版本）未测：`node:sqlite` 在 Node 24 仍为 experimental，若校方服务器为 Node 20，需替换存储驱动；改动集中在 `src/store/`。

## 8. 明确没做的事

- 没有 HTTP 接口、没有前端页面
- 没有通知发送（只有事件记录）
- 没有角色权限判定（`Principal` 校验在 P5）
- 没有争议裁决、卡单处理、升级代理
- 没有自动生成恢复方案的反向条目
- 没有批量调课、没有推荐候选教师
- 没有读取任何学校真实数据
