# 课表查询可索引化（P7M）

## 1. 起因

`swapCandidates`（对调对象推荐）在正式库单次 361ms。T-08 是 200 人并发，
这个量级在 Node 单线程 + 同步 SQLite 下会直接排队，所以先解决它。

## 2. 先量，再改

正式库：`TERM-2026-08-31`，57 班 / 26 科 / 1938 条有效模板 / 40698 条课次。

| 查询 | 改造前 | 改造后 |
|---|---|---|
| `queryAll` 全学期（40698 行） | 337–430ms | 266ms |
| `queryByTeacher` 全学期（378 行） | 65ms | 2.0ms |
| `queryByClass` 全学期（约 700 行） | 5.2ms | 5.1ms |
| 9 位教师整学期（对调推荐） | 99ms | 0.1–25ms（取决于是否排序） |
| 单日全教师（`suggest` 用） | 57.6ms | 3.2ms |
| `swapCandidates` | 361ms | 34ms |
| `suggest` | 78ms | 9–11ms |

`EXPLAIN QUERY PLAN` 给出了原因：

```
改造前：SEARCH o USING INDEX idx_occ_class (term_id=?)      ← 只用到 term_id，等于整学期扫
改造后：SEARCH o USING INDEX idx_occ_teacher (term_id=? AND teacher_id=? AND date>? AND date<?)
```

`COALESCE(st.date, o.date)` 对 SQLite 的索引选择器是不透明的，只要谓词里出现它，
`idx_occ_teacher` / `idx_occ_class` 就只能用 `term_id` 前缀，剩下的全表过滤。

## 3. 改法：base ∪ overlay 两段

有效课次 = 派生课次 `occurrence` 叠加已生效变更 `assignment_state`。改成两段 `UNION ALL`：

```sql
-- 第 1 段：没有覆盖行的课次，按 o.* 过滤，命中 idx_occ_*
SELECT ... FROM occurrence o JOIN class/teacher/subject ...
 WHERE o.term_id = ? AND o.teacher_id IN (...) AND o.date BETWEEN ? AND ?
   AND NOT EXISTS (SELECT 1 FROM assignment_state x WHERE x.occurrence_id = o.id)
UNION ALL
-- 第 2 段：有覆盖行的课次，按 st.* 过滤，命中 assignment_state 的索引
SELECT ... FROM occurrence o JOIN assignment_state st ON ... JOIN class/teacher/subject ...
 WHERE st.term_id = ? AND st.teacher_id IN (...) AND st.date BETWEEN ? AND ?
```

两段合起来与 `COALESCE` 版本**严格等价**：

- 无覆盖行 → 第 1 段负责，按原始教师/日期；
- 有覆盖行 → 第 2 段负责，覆盖行写全了教师/日期/节次/停课；
- 某节课被改期到区间内、原始日期在区间外 → 只有第 2 段能取到，这正是**必须按 `st.date` 过滤**的原因；
- 某节课被改期到区间外 → 第 1 段因 `NOT EXISTS` 排除，第 2 段因 `st.date` 越界排除。

新增索引：

```sql
CREATE INDEX idx_occ_term_date       ON occurrence(term_id, date);          -- 某天全校
CREATE INDEX idx_assignment_teacher  ON assignment_state(term_id, teacher_id, date);
```

`idx_occ_term_date` 之前不存在，所以"取某一天全校课表"（`suggest`、课表页）只能按 `term_id` 扫全学期。

## 4. 推荐路径只取需要的教师

`swapCandidates` 原本先 `queryAll(term, from, to)` 把整学期四万行搬进内存再按教师分组。
但按现有口径（docs/13 §7.8）只有**同班教师**会被逐节评估，其余人的理由只有一句"不任教该班"。
改为一次 `queryByTeachers(同班教师 + 我)`：一1 班 8 位任课教师，2625 行，而不是 40698 行。

`queryByTeachers` 不排序：唯一调用方是推荐计算，它自己会按日期/节次重排；
整段排序对 2625 行要多花约 10ms，属纯浪费。需要有序结果请用 `queryAll` / `queryByClass`。

## 5. 为什么不用向量检索

考虑过，但不适用：

1. **这是精确约束，不是相似度**。同班、同科、时段不撞、当天课数上限，都是硬条件；
   ANN 检索给出的是"最近邻"，不是"满足条件的全集"。
2. **召回率不够就等于静默丢人**。常见向量索引在 40k 规模下召回约 95–99%，
   意味着每 20–100 次推荐就有一位合法教师悄悄不出现——直接违反"名单不允许有人悄悄消失"。
3. **不可解释**。推荐必须能逐条说出理由（同班 / 同科 / 当天几节 / 连续几节），
   嵌入向量的距离给不出这些句子。
4. **规模不匹配**。40698 行、全部字段约 17MB，SQLite 一次索引查询就是亚毫秒级；
   为这个量级引入向量库，只增加依赖、构建时间和一致性风险。

同一类"预计算"的思路有更合适的落点，按收益/风险排序：

| 方案 | 单次耗时 | 代价 | 结论 |
|---|---|---|---|
| 索引可命中（已做） | 34ms | 无缓存，永远读最新 | ✅ 采用 |
| 进程内只读快照（按学期分桶） | ~0ms | 需要失效策略；失效不严会读到旧课表 | 留待 T-08 实测不够时再上 |
| 物化 `occurrence_effective` 表 | ~1ms | 写路径要同步维护，易与审计事实分叉 | 不推荐 |

优先选前者：本系统的整个价值建立在"给教师看到的课表必须是当下的"，
用缓存换 34ms 不值得拿这个换。

## 6. 验证

- `tests/store/effective-query.spec.ts`：逐条钉住换教师 / 改期 / 停课 / 批量与全校逐行一致；
- `tests/store/views-consistency.spec.ts`：1000 组随机校历，教师视图与班级视图逐行一致（原有）；
- 全量 463 个测试通过，`tsc --noEmit` 无输出；
- 演示环境端到端：`/api/changes/swap-candidates` 200，18–35ms。

## 7. 尚未解决

- `queryAll` 全学期仍要 266ms：调用方（课表页整学期视图）确实需要全部行，属固有成本。
  若 T-08 压测显示课表页是瓶颈，再评估分页或快照缓存。
- `swapCandidates` 剩余 34ms 中约 10ms 在 `activeTemplates`（1938 行）+ 逐行对象化，
  已无索引问题，属 JS 侧成本。
