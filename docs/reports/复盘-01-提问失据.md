# 复盘：一次无依据的业务提问

- 日期：2026-10-31
- 触发：项目负责人要求"不要忽略这个错误，审核为什么会出现"
- 结论：不是措辞问题，是**提问前不回原文核对**的稳定倾向；错误已进入交付物，已修正。

---

## 1. 事实

P3 结束交接时，我提出：

> P4 开工前需要项目负责人确认一件事：**变更生效时，是否允许在课表已有排课的时段插入？** 我的默认是按"结构冲突硬拒绝、需先调整排课再发起变更"实现。

并随后给出三个选项，第一项标注"推荐"。

该问题已写入 `docs/reports/P3-报告.md` 第 150 行，也写入了工作记录。

项目负责人追问后，我核对 V2.3 §4.2：

> 必要确认者：仅本次方案中授课责任或工作任务被实际改变的教师。系统从受影响课务计算，不固定为两名，不由发起人随意指定。

**问题前提不成立。** 目标时段已有课，不是拒绝理由；它只是让该时段原有教师成为必要确认者之一。问题已撤回，未写入代码。

---

## 2. 为什么这是错误，而不是"问得不够清楚"

若按我当时的默认实现，后果是具体的：

1. **直接封死最常见的调课形式。** V2.3 工程边界必测场景 3 就是"两名或多名教师互换课程"。互换必然占用对方原有课时段。按"结构冲突硬拒绝"，互换根本无法发起。
2. **新增一条学校从未确认的限制。** 这违反项目第一原则：不得自行补充学校没有确认的管理制度。
3. **错误会被固化。** 一旦写进报告并被引用，后续会有人把它当作"已确认规则"实现，届时纠正成本远高于现在。

第 3 点已经发生了一半：它在 P3 报告里放了几十分钟。

---

## 3. 直接原因：用通用排课模型替代了本项目的领域模型

我脑子里的模型是通用排课系统：

```
一个格子 = 一个班级 × 一个时段
一个格子只能放一节课
两节课撞同一格 = 冲突 = 拒绝
```

本项目 V2.3 的模型不是这个：

```
课次是"某一日某一节由谁对哪个班负责"
调课方案描述的是"变更后的完整结果"
必要确认者 = 责任被实际改变的人
冲突校验发生在生效前复核，不是提交前禁止
"同一格两节课"只出现在方案描述不完整时，是"算不出结果"，不是"业务禁止"
```

我拿前者的约束去问后者的制度。这是**领域模型错位**，不是粗心。

---

## 4. 更深的原因（按严重度排序）

### 4.1 建了台账，却不查台账

`docs/traceability.csv` 第 17 行：

```
D1,调课,必要确认者由受影响集合计算,V2.3-01 §4 R01,C,V23-03,spec/v23.spec.ts,verified
```

答案就在我自己建的追溯表里，一条 `grep 调课` 就能命中，状态还是 `verified`——说明 P1 时我已经把它写成了可执行反例。

但我提问时用的是**对话记忆 + 通用常识**，不是台账。

这说明一个更根本的问题：**我把 traceability.csv 和 decisions.csv 当成了交付物，而不是工作工具。** 建完、提交、报告里提一句"47 行"，然后就不再使用它。台账的价值在于"提问前查一次"，我一次都没查。

### 4.2 把实现层约束当成业务制度

"同一班同一时段不能同时有两节课"是数据完整性要求，属于实现层，由我可以直接决定。

学校要决定的是"谁的责任变了、谁同意了"，不是"格子能不能重叠"。

我把前者包装成后者去征询学校，等于让学校为一个技术问题背书——而且是一个我理解错了的技术问题。

### 4.3 用"我有默认方案"制造确定性错觉

原话里有"**我的默认是**按结构冲突硬拒绝"。

这句话让问题看起来像"我已经想清楚了，只差你点头"，实际上掩盖了"我根本没有依据"。

**"有默认值"被当成了"有依据"。** 这是最危险的一条：它同时骗过了我和读者。如果我当时写的是"我不确定这里该怎么处理"，我自己就会去查原文。

### 4.4 阶段交接的仪式压力

每个阶段结束，我倾向于抛一个"待确认项"作为交接动作。

当真实 OPEN 项不属于当前阶段时，这种压力会促使我把非问题包装成问题。后果是稀释 40 项真实待决事项的注意力，并让项目看起来比实际更不确定。

### 4.5 "推荐"标签放大了危害

即使负责人隐约觉得不对，看到"推荐"也会倾向选第一项。这等于我用选项设计代替学校做决定——而这正是第一原则禁止的行为。

不只这一次。逐条回查我做过的业务提问：

| 时间 | 提问 | 判定 |
|---|---|---|

| P3 结束 | 调课是否允许插入已有课位置 | **明确错误**，前提不成立。 |
| P2 前 | 后端栈 Node/Python | 成立。原文未定，属技术选型。 |
| P2 | 首周单双周基准 | 成立。原文未定，已按"未配置即 UNKNOWN"处理。 |

技术类问题我做得较好——会去查环境、查版本、写测试验证。业务类问题我依赖记忆和常识，因为"看起来我读过"。

## 6. 纠正措施

### 6.1 提问前置三问（已写入 `docs/01` §6）

1. **原文哪一段？** 说出文件名与章节。说不出，不得提问。
2. **台账哪一行？** `traceability.csv` / `decisions.csv` 有对应 ID 吗？
3. **两者都没有时**，它是"原文明确未定"还是"我自造"？自造的不得提问。

### 6.2 台账是唯一合法来源

`decisions.csv` 是待决事项的唯一合法清单。要新增，先加行并注明来源，不得只在对话里抛出。

### 6.3 数据一致性约束不进业务提问

"同一班同一时段两节课"这类问题由实现层解决，不问学校。

### 6.4 阶段结束允许"无阻断项"

没有真实阻断时，直接写"本阶段无阻断项"。不为交接硬凑问题。

### 6.5 给"推荐"前自问

这个推荐是否在替学校做决定？若是，改为陈述事实与后果，不给推荐。

### 6.6 禁止用"我的默认是"替代依据

提业务问题时不写"我的默认是……"，改写成"原文 §X 规定……；此处原文未覆盖，需要你确认"。前者掩盖无依据，后者暴露无依据。

## 8. 这次错误对 P4 的实际影响

零行代码受影响（P4 尚未开工），但设计口径被纠正了一条：

- **原（错误）**：调课只能调到双方都空的时段。
- **现（正确）**：方案必须描述变更后的完整结果；系统据此计算责任变化集合；集合内每人本人确认；生效前复核冲突。目标时段原有教师若责任被改变，自然进入确认集合。

P4 不需要项目负责人就此事做任何裁决。
