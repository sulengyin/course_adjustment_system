# 版本、提交与协作规范

- 生效日期：2026-11-04
- 适用：本仓库的全部提交（含自动化工具产生的提交）
- 目的：让"现在部署的是哪一版""这行代码为什么这么改""回滚会丢什么"三个问题能在**不依赖记忆**的情况下回答

## 0. 三条前提

规则不是通用的，是从这三条事实推出来的：

| 前提 | 后果 |
|---|---|
| 仓库**公开**（GitHub，无私有仓库） | 任何写入 `main` 的内容等于对外发布，口令与内网细节一律不进文档 |
| 主要**单人维护** | 不引入 PR 评审流程的强制开销，但保留高风险改动的闸门 |
| 真实数据**在内网、不在仓库** | 代码回滚 ≠ 数据回滚，涉及 DDL 的提交必须单独说明数据侧处置 |

## 1. 分支策略

采用 trunk-based，`main` 是唯一长期分支。

### 1.1 `main` 的硬标准

任何时刻检出 `main` 都必须满足：

1. `npm run typecheck` 通过；
2. `npm test` 全绿；
3. 能按 README 启动。

达不到就说明这次提交不该进 `main`，而不是"先合了再说"。

### 1.2 什么时候开分支

| 改动 | 做法 |
|---|---|
| 文档、文案、单个缺陷 | 直接提交 `main` |
| **动 DDL、权限模型、部署脚本** | 开短命分支，验证通过再合 |
| 探针、一次性排查脚本 | 不进仓库，放 `.run/` |

三类高风险改动的共同点：出错时会影响**已经在用的真实数据**或**正在服务的实例**。

### 1.3 分支规则

- 命名：`<阶段编号>-<英文短名>`，如 `p7q-on-behalf`。不用 `feature/`、`fix/` 长前缀，单人维护没有必要。
- 生命周期：不超过 3 天。到期未合并就说明它太大，拆小。
- 合并：保持线性（rebase 或 fast-forward），不制造 merge commit——单线历史更容易用 `git log` 回溯。
- 合并后立即删除分支，本地与远端都要删。

## 2. 提交规范

### 2.1 标题

格式：`中文动词短语（P7X）`

- 说清**做了什么**，不是"修改""更新""优化"这类无信息量动词。
- 结尾是**唯一的阶段编号**，取自 `docs/01` 阶段表。
- 标题不超过 40 个汉字。超了说明这次提交包含多个主题，应拆分。

### 2.2 正文

三段，缺一段也算不合格：

1. **为什么**：触发这次改动的事实、缺陷现象或需求来源。
2. **影响面**：改了哪些行为、哪些接口、哪些表；有库变更时写明**是否需要迁移**、**回滚会丢什么**。
3. **怎么验**：跑了什么命令、结果如何。可以是一行。

纯文档提交以 `文档：` 开头，便于 `git log --grep` 过滤。

### 2.3 拆分与验证

**一个提交 = 一个可回滚单元**，判断标准是"单独 revert 它，系统仍然能编译、测试仍然绿"。

拆完必须**逐提交检出验证**，不能只看工作区最终态：

```bash
# 在仓库外的临时目录检出某个提交，确认它自己能不能编译
V=<临时目录>/ca-verify
git worktree add --detach "$V" <sha>
ln -sfn "$PWD/node_modules" "$V/node_modules"
(cd "$V" && npx tsc --noEmit)
git worktree remove --force "$V"
```

这条不是形式主义：2026-11-04 曾把 `grant-capability.ts` 放在只含启动脚本的提交里，
它调用的方法在后一个提交才存在；工作区 `tsc` 干净，**只有单独检出才暴露**。

### 2.4 编号必须先登记

新编号先写进 `docs/01` 阶段表，再出现在提交信息里。
只在 `traceability.csv` 出现、阶段表里没有的编号，视为未登记——`P7Q`/`P7R`/`P7T` 就踩过这个坑。

## 3. 版本与发布

### 3.1 版本号

`0.x.y`，内部迭代，不承诺对外 API 兼容。**不要为了"看起来正式"跳到 1.0.0。**

| 位 | 何时进位 |
|---|---|
| `x` | 改变业务语义：新增能力、修改权限模型、变更默认行为 |
| `y` | 缺陷修复、文案、样式、性能，不改变使用者理解的行为 |

### 3.2 tag

只在**上过生产的那次提交**上打 annotated tag，注释必须写三件事：

```bash
git tag -a v0.3.0 <sha> -m "v0.3.0

库变更：新表 capability_grant、change_case 新增 created_by、四组索引（启动自动补齐）
兼容性：旧代码可读新库，但写 change_case 不填 created_by
回滚：退回 0.2.0 会使『代发起』静默退化为『本人发起』，回滚前须确认无在途方案"
```

tag 不打在"最后一次提交"，打在"已经部署验证过的那次提交"——两者常常不是同一个。

### 3.3 CHANGELOG

`CHANGELOG.md` 按 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 组织，
只写对使用者有意义的变化，不逐条抄提交日志。

每个版本至少覆盖：新增 / 修复 / 变更 / 升级注意。**升级注意里必须回答"要不要迁移"和"回滚会丢什么"。**

## 4. 仓库结构

根目录只允许出现：`README.md`、`LICENSE`、`CHANGELOG.md`、`package.json`、`package-lock.json`、
`tsconfig.json`、`.gitignore`，以及下列目录。

| 目录 | 放什么 | 不放什么 |
|---|---|---|
| `src/` | 产品实现 | 一次性排查逻辑 |
| `spec/` | 可执行规格与参考实现 | 从正式库复制的数据 |
| `tests/` | 实现侧测试 | 需要人工观察的验收记录 |
| `web/` | 前端源码 | 构建产物（本项目无构建） |
| `scripts/` | 运维、导入、种子脚本 | 临时探针（放 `.run/`） |
| `docs/` | 决策、依据、验收记录 | 运行日志、截图原件 |

`docs/reports/` 命名统一为两种：

- `<编号>-报告.md` —— 阶段收尾，如 `P7A-报告.md`
- `<编号>-<专项>.md` —— 单项验收，如 `P7Q-T04-实机验收.md`

不再新增第三种写法。

## 5. 敏感信息

### 5.1 三级分类

| 级别 | 内容 | 处置 |
|---|---|---|
| **L1 绝不入库** | 库文件、真实名单、口令、备份、导出的原始表格 | `.gitignore` + CI 检查 + 人工复核 |
| **L2 不写具体值** | 内网 IP、端口、数据库绝对路径、数据归档目录 | 文档写 `192.168.x.x`、`<DB_PATH>`、`<DATA_ARCHIVE_DIR>` |
| **L3 测试数据** | 教师姓名、手机号、班级编号 | 只用虚构值（`示例教师乙`、`13800138000`） |

平台固定路径（如 OpenHarmony 的工具链目录）不属于 L2：它对所有同型号设备都一样，不构成拓扑信息。

### 5.2 为什么要分三级

不分级的清单最后会变成"什么都不敢写"，文档随之失去可操作性。
真正需要挡住的只有两样：**能直接登录的凭据**，和**能拼出攻击面的拓扑**。

### 5.3 误提交的处置顺序

**先轮换，再洗历史，最后通知。顺序不能反。**

1. 停用或重置涉事账号、口令、密钥；
2. 需要时用 `git filter-repo` 清洗历史（会改写全部后续 commit 的 hash，需强推）；
3. 通知受影响的人。

只删除文件而不轮换，等于没处理——公开仓库的历史可以被任意克隆。

判定标准很实际：**IP 和路径不是凭据，改文档即可，不必洗历史；口令是凭据，必须先轮换。**
2026-11-04 处理 `docs/reports/P7-T04实机验收清单.md` 的明文演示口令时按后者执行。

## 6. 协作约定

### 6.1 人的边界

- 只有仓库所有者能推送 `main`。
- 自动化工具（含 AI 助手）只做本地提交：**不主动 push、不改写已推送历史、不删除分支**。
  需要重写历史时必须先说明理由并取得同意。

### 6.2 每次交付说什么

三句话，缺一不可：

1. 改了什么（用户能感知的行为变化）；
2. 影响谁（哪些角色、哪些数据、哪些部署）；
3. 怎么验（命令与结果，不是"已完成"）。

### 6.3 提交前清单

- [ ] 标题与正文符合 §2
- [ ] `npm run typecheck` 通过
- [ ] `npm test` 全绿
- [ ] 新增文件里没有数据库、日志、真实名单
- [ ] 涉及 DDL 时，正文写了迁移与回滚
- [ ] 拆分过的提交，逐个检出能编译

### 6.4 上线前清单

顺序固定，不跳步：

1. 备份库（`npm run backup`）；
2. `npm run typecheck` 与 `npm test`；
3. 重启两个实例（`npm run serve:auto`）；
4. 冒烟：正式实例能登录、课表能出、审计条数在增长；
5. 在 `docs/reports/` 留一条记录（日期、版本、结果）。

### 6.5 回滚

- 一律用 `git revert <sha>`，不用 `reset --hard`，更不要强推覆盖。
- 涉及 DDL 的回滚，除代码外还要说明数据侧：**新列/新表可以留着，旧代码能读；但写入语义可能退化。**
- 回滚后必须重跑一次上线前清单——回滚本身也是一次变更。

## 7. 这份规范怎么改

规则不合适就改，但要走同样的流程：开分支、改本文档、在提交正文里写清"为什么原规则不好用"。
不允许"这次特殊，先绕过"——绕过一次，规范就失效了。
